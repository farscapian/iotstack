iotstack rotate-secrets -- Additional Documentation

Extended reference for secret rotation: when to rotate, rollout order across
devices, and how version history is kept in pass.

Why Rotate Secrets?
===================

Regular secret rotation is a security best practice:

  1. Limits exposure window if password is compromised
  2. Prevents long-term use of same password
  3. Creates audit trail of when changes occurred
  4. Allows gradual rollout (update devices slowly)

In iotstack:
  - Recommended: Rotate every 30-90 days
  - Or: Whenever someone with access leaves
  - Or: After any security incident
  - Versioning allows bootstrap of old passwords


Versioning System
=================

Each time you rotate, a new version is created automatically:

Generation:
  1. Run: iotstack rotate-secrets bleproxy
  2. New password generated (or use custom)
  3. Stored in pass with version number
  4. Old password archived for recovery

Version numbering:
  v0 (initial)  -> First secret when device was set up
  v1            -> First rotation
  v2            -> Second rotation
  etc.

Retrieving old versions:
  iotstack secret get bleproxy ota        # Current (latest)
  iotstack secret get bleproxy ota 0      # v0 (archived)
  iotstack secret get bleproxy ota v0     # v0 (same, alternate syntax)
  iotstack secret get bleproxy ota 1      # v1 (if exists)

This allows:
  [OK] Recovery if you need old password for some reason
  [OK] Audit trail (can see all password changes)
  [OK] Gradual rollout (devices can keep using old password until updated)


Device Update Sequence
======================

After rotating secrets, devices need to be updated to get the new password.

Timeline:
  1. Run: iotstack rotate-secrets bleproxy
     -> New password generated and stored in pass
     -> Old devices still have old password (in NVS)

  2. Run: iotstack update bleproxy
     -> Devices get new firmware with new password in NVS
     -> Device boots with new password

  3. All devices now have new password
     -> Old password won't work anymore

This means:
  [OK] Devices can be updated gradually
  [OK] You can verify new password before rolling out
  [OK] No downtime (each device reboots briefly during OTA)


OTA vs API Keys
===============

Two different secrets are maintained:

1. OTA Password:
   - Required for firmware updates via OTA
   - One per role (shared by all devices in that role)
   - Device-specific version: sha256(role_password + MAC)
   - Always rotated (required)

2. API Encryption Key:
   - Used for encrypted communication with Home Assistant
   - One per role
   - Only used if HA_URL and HA_TOKEN are configured
   - Optional (skipped if HA not configured)

When you run 'iotstack rotate-secrets':
  - OTA password: Always rotated
  - API key: Only if HA is configured

You can verify:
  iotstack secret get bleproxy ota       # OTA password
  iotstack secret get bleproxy api       # API key (if configured)


Security Implications
=====================

OTA passwords:
  - Device-specific (derived from role secret + MAC)
  - Stored in device NVS (plaintext, not encrypted by default)
  - Transmitted over network during OTA
  - Protects against unauthorized firmware updates

API keys:
  - Shared by all devices in a role (same key)
  - Stored in pass (GPG encrypted)
  - Sent during device boot via NVS
  - Protects HA API communication

Threats mitigated:
  [OK] Unauthorized firmware updates (OTA password)
  [OK] Replay attacks (new password each rotation)
  [OK] Privilege escalation (device-specific passwords)

Threats NOT mitigated:
  [FAIL] Physical device extraction (NVS plaintext in flash)
  [FAIL] Network sniffing during OTA (consider VPN if needed)
  [FAIL] Home Assistant compromise (API key in HA)


Custom vs Generated Passwords
=============================

Generated passwords (default):
  - 32 characters, cryptographically random
  - Mix of alphanumeric characters
  - Safe and unpredictable
  - Recommended for most cases

Custom passwords:
  iotstack rotate-secrets bleproxy "myCustomPassword123"

  Use when:
  - You need a password you can remember
  - Integrating with other systems
  - Debugging/testing
  - Following corporate policies

Minimum requirements:
  - At least 12 characters recommended
  - Can contain any printable characters
  - No special URL-encoding needed


Automation & Integration
========================

Getting current password for automation:
  PASSWORD=$(iotstack secret get bleproxy ota)
  # Use $PASSWORD in scripts, ansible, etc.

Or in bash scripts:
  iotstack secret get bleproxy ota | xargs -I {} echo "Password: {}"

Or export for external tools:
  export BLEPROXY_OTA_PASSWORD=$(iotstack secret get bleproxy ota)
  ./external-tool.sh $BLEPROXY_OTA_PASSWORD

Example: Update specific devices programmatically:
  for mac in a1a7b0 8e1aa8; do
    pwd=$(iotstack secret get bleproxy ota)
    iotstack update "$mac" bleproxy --ota-password "$pwd"
  done


Disaster Recovery
=================

If you lose the current password:
  1. Check pass store for archived version:
     pass show iotstack/roles/bleproxy/ota_password/v*

  2. If pass store is lost, you can't recover passwords

  3. Emergency: Flash bootstrap image via serial
     iotstack flash bootstrap /dev/ttyUSB0
     (recovery uses universalrecovery.yaml, not affected by password)

Backup strategy:
  - Export pass store to encrypted backup
  - Keep versioned passwords (they're archived)
  - Document in password manager (separately from pass)
  - Test bootstrap procedure annually
