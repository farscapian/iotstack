iotstack flash -- Serial bootstrap flash + OTA production setup

USB/serial writes the partition table and bootstrap partition only. Production
firmware is always delivered over OTA after the device boots into bootstrap.

Usage:
  iotstack flash <device> [tty-device...] [options]
  iotstack flash bootstrap [tty-device...|role]

Arguments:
  <device>        Device role (e.g., bleproxy, mmwave, threadrouter)
  bootstrap        Flash bootstrap image via serial (partition table + bootstrap)
  [tty-device...] One or more serial devices (e.g., /dev/ttyACM0). Multiple
                  ports are flashed ONE AT A TIME (serially, never in parallel):
                  each device completes its full bootstrap + OTA cycle before
                  the next begins. Omitted: auto-pick from NVS device_role on
                  USB ports, or the only port with a matching chip variant
                  (e.g. matrixdisplay = esp32s3). New/unprovisioned devices
                  need an explicit tty.
  [role]          Production role for dual-flash (e.g., mmwave, bleproxy)

Options:
  --ota-only      Skip serial bootstrap flash; compile and OTA production only
                  (device already has bootstrap on flash)
  --on-flash-verify
                  Compare firmware by reading flash over USB (slower, more
                  thorough). Default uses runtime mDNS config_hash (same as
                  iotstack devices --production).
  --erase         Wipe flash partitions then reflash bootstrap via serial

Role-specific options (e.g. matrixdisplay HUB75 NVS layout):

  iotstack help <role>              e.g. iotstack help matrixdisplay
  iotstack flash <role> help        same file for flash / update / reassign

NVS secrets (WiFi, OTA password, API key, matrix layout, etc.):
  iotstack prefers updating NVS over the network -- switch to bootstrap, then
  call the update_nvs_secrets API service on bootstrap-<mac>.local. USB
  (write-nvs-secrets.sh / esptool) is used only when bootstrap is not yet on
  WiFi (typical first serial provision) or the API is unavailable.

Smart flash (default):
  1. Build bootstrap + production images (production is for OTA only).
  2. Assess device (mDNS / optional USB read-flash verify).
  3. Serial: partition table + bootstrap if needed (never production).
  4. iotstack update -- same flow as `iotstack update <role> <mac>` (OTA into
     the production partition from bootstrap; never serial).

  Production OTA is skipped when runtime config_hash already matches the
  build. Serial erase/reflash runs only when the on-device partition table
  or bootstrap image differs from the current build.

  Use --on-flash-verify to compare by reading bootstrap/production partitions
  over USB (adds ~1-2 minutes; production read is assessment only, not write).

Examples:
  iotstack flash bleproxy /dev/ttyUSB0           # Serial bootstrap + OTA prod
  iotstack flash bootstrap mmwave                 # Dual: serial bootstrap + OTA mmwave
  iotstack flash bootstrap /dev/ttyUSB0           # Bootstrap serial only
  iotstack flash mmwave /dev/ttyACM0 --ota-only  # OTA production only
  iotstack flash mmwave /dev/ttyACM0 /dev/ttyACM1 /dev/ttyACM2 --erase
                                                 # 3 devices flashed serially, one at a time
  iotstack flash matrixdisplay help              # Role-specific flash options
  iotstack flash threadrouter                    # Auto-detect all USB devices
