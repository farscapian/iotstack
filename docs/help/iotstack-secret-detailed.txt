iotstack secret — Additional Documentation

Secret Storage Architecture
============================

Secrets are stored in three places:

1. Pass Store (~/.iotstack/.pass/):
   - Master encrypted password manager (GPG)
   - Role-based secrets (e.g., iotstack/roles/bleproxy/ota_password)
   - Version history for each secret (v0, v1, v2, etc.)
   - Most secure: encrypted at rest, encrypted in transit

2. Device NVS (Non-Volatile Storage):
   - Device flash memory partition (0x9000)
   - Device-specific secrets derived from role secret + MAC
   - Persists across firmware updates
   - Plaintext in flash (not encrypted by default; see flash encryption docs)

3. Firmware Binary:
   - NEVER compiled into firmware (we extract at runtime)
   - OTA password comes from NVS, not from YAML
   - WiFi credentials come from NVS, not from YAML

This separation means:
  ✓ No password disclosure if firmware is extracted
  ✓ Unique password per device even with single firmware
  ✓ Passwords persist across OTA updates (in NVS)
  ✓ Old passwords accessible for recovery


Versioned Secrets
=================

Each time you rotate secrets, a new version is created:

  Version 0 (v0):      Initial secret (when device first configured)
  Version 1 (v1):      First rotation
  Version 2 (v2):      Second rotation
  ... and so on

This allows recovery of old passwords:

  iotstack secret get bleproxy ota              # Current version
  iotstack secret get bleproxy ota 0            # v0 (archived)
  iotstack secret get bleproxy ota 1            # v1 (archived)

Use cases for old versions:
  - Device has old password, need to recover it
  - Audit trail (when was this changed?)
  - Gradual rollout (update devices slowly using current version)


Secret Types
============

Two types of secrets:

1. OTA Password (ota):
   - Required for updating devices
   - Automatically rotated with each 'iotstack rotate-secrets'
   - One per role (all bleproxy devices share same password)
   - Device-specific version: sha256(role_password + device_mac)

2. API Encryption Key (api):
   - Used for Home Assistant API communication
   - Only used if HA is configured
   - Automatic encryption/decryption by ESPHome
   - Rotated with 'iotstack rotate-secrets' if HA configured


Retrieving Secrets
==================

Get the current OTA password for a role:
  iotstack secret get bleproxy ota

Get a specific version:
  iotstack secret get bleproxy ota 0

Get API encryption key:
  iotstack secret get bleproxy api

Output format:
  Prints the secret to stdout (plain text)

Common use cases:
  - Pass to manual device updates
  - Backup/export for disaster recovery
  - Integration with external tools


Rotating Secrets
================

Always use 'iotstack rotate-secrets' to generate new passwords:

  iotstack rotate-secrets bleproxy

This automatically:
  - Generates a cryptographically secure password (32 chars)
  - Stores it in pass with version numbering
  - Writes it to device NVS on next update
  - Updates Home Assistant if configured

For manual password specification:
  iotstack rotate-secrets bleproxy "customPassword123"

After rotation:
  - New devices get new password
  - Old devices keep old password until updated
  - You can verify: iotstack secret get bleproxy ota


Security Implications
=====================

Threats protected:
  ✓ Firmware extraction: Attacker can't get password (not in binary)
  ✓ Binary analysis: No hardcoded secrets (comes from NVS)
  ✓ Single password for all: Each device unique (derived from MAC)

Threats NOT protected (NVS is plaintext):
  ✗ Physical flash extraction: NVS data is readable
  ✗ But requires: USB programmer, technical skill, physical access

Mitigation (future):
  - Enable flash encryption (eFuses) for production
  - See: docs/flash-encryption.txt
